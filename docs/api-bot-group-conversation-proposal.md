状态：产品方向已确认，主要模块已接入，正在修复和验收。实际进度见
[api-bot-group-conversation-implementation.md](api-bot-group-conversation-implementation.md)。
日期：2026-09-14（评审 2026-09-15；实施核对 2026-09-27）。

## 当前接入模型（2026-09-27）

Bot 是有身份的会谈成员，可以绑定本地 CLI Agent，也可以绑定自定义 API。两类成员可混合会谈：本地 Agent 复用自身登录、默认模型与配置；API Bot 独立保存服务地址、模型和加密凭据。旧共享 API Bot 继续兼容，不要求本地 Agent 先填写全局 API Key。

创建流程为“选择本地 Agent / 自定义 API → 配置或安装登录 → 创建 Bot → 加入会谈”。本地目录包含美国的 Codex CLI、Claude Code、Gemini CLI，以及中国的 Qwen Code、Kimi Code CLI。未安装时展示官方命令，可打开系统终端安装、登录、查看指南并重新检测；找到文件不等于能够启动，也不等于已经登录。

本地 CLI 并不等于离线模型。订阅额度、API 计费和模型权限取决于该 Agent 的实际登录及服务配置。当前会谈不自动批准工具写入或命令执行请求；允许用户选择工作目录，留空使用独立临时目录。无需内置完整终端才能使用 CLI 会谈。

以下原 API 方案中的单一服务入口、API-only Bot 与 CLI 混合会谈后置边界，均由本节替代。多轮上下文、有限轮次、停止、重试和本地历史的要求继续有效；实际完成情况见实施文档。

参考上游 `0f69395f64ba7f28d6c7e268343bbadc08bf1105` 的 `AgentWorkspace.tsx`、`agentRuntime.ts`、`agentDetection.ts` 和 `acpRuntime.ts`：采用 Bot 身份与运行方式分离、已安装运行时检测、API 接入并列的设计。当前分别通过 Codex JSONL、Claude 非交互接口和 Gemini/Qwen/Kimi ACP 接入；不声称完整复刻上游工作台或权限交互。

## 1. 目标与调整范围

API 会谈改为以 Bot 和群聊为中心：用户创建绑定模型的 Bot，将多个 Bot 加入同一会谈，一次提问即可获得多方回答，再按需要指定回应、互评和总结。讨论过程保留完整记录，用户不必在模型之间手动转发。

第三方聚合平台是第一版明确支持的接入方式：用户配置一个平台的 API Key，为不同 Bot 选择该平台提供的不同模型，即可进行多方会谈，无需逐个安装官方 Agent 或分别申请各模型厂商的 Key。可用模型取决于所选平台及账号权限。

本方案仅调整当前项目的 API 会谈。内嵌官网、官网转发、现有长期记忆继续独立可用。继续使用当前桌面应用底座，参考 Termany 的产品设计并独立实现，不复制其源码，不引入其完整工作台、终端或 Agent 运行时。

Bot 会谈直接替代旧 API 分屏模式，保留“内嵌官网 / Bot 会谈”两种入口，不另增第三种 Agent 模式。API 地址、Key 和模型选择属于 Bot 会谈的服务配置。设计文档 §3.4 和 AGENTS.md 已同步这一方向；主要界面已接入，入口名称已统一，旧分屏调用逻辑仍待清理。第一版 Bot 的能力边界见 §3 和 §11。

## 2. 改造前基线与目标

下表记录 2026-09-14 制定方案时的改造前状态，用于说明调整原因，不代表当前实施进度。当前实现与验收缺口以[实施状态](api-bot-group-conversation-implementation.md)为准：

| 项目 | 改造前实现 | 本次目标 |
|---|---|---|
| 模型配置 | 一个兼容服务入口、一个 Key、多个模型，模型绑定格子 | 沿用服务配置，模型绑定 Bot |
| 第三方平台 | 已有第三方服务入口和模型发现，但模型目录受品牌与推荐规则筛选 | 明确支持一个平台 Key 调用多个模型；推荐列表不限制可选模型 |
| 回答 | 并发请求、流式展示 | 保留，并按 Bot 展示消息 |
| 历史 | 格子保存最新回答；普通提问仅发送本次问题 | 保存多轮会谈，追问携带相关历史 |
| 互评 | 手动转发源格子的回答 | 群内指定回应或发起互评一轮 |
| 总结 | 基于可见格子的最新回答生成，覆盖总结者格子的内容 | 基于会谈记录生成独立总结消息，保留原回答 |
| 持久化 | 已保存 API 配置；当前回答在界面内存中 | 本地保存 Bot、会谈和消息 |

API 流式输出和手动触发总结已经存在，本次继续完善，不作为全新能力重新开发。

## 3. 核心对象

### Bot：可以重复加入会谈的 AI 成员

每个 Bot 包含名称、模型和可选的角色说明。例如“方案顾问”“挑错助手”；角色说明用于说明关注点，不要求用户必须设置角色。

- 创建时直接选择已配置服务中的模型，不增加“Termany”一类需要用户猜测含义的中间入口。
- 名称可编辑；始终同时展示真实模型，避免把不同名字误认为不同模型。
- 成员详情同时显示提供调用服务的平台和完整模型 ID，区分“在哪个平台调用”与“使用哪个模型”；快照保留这些身份信息，不包含 Key。
- 允许同一模型创建多个角色不同的 Bot，并提示“使用相同模型”；不同角色不保证观点独立。
- 模型不可用时明确标记，允许用户改选；不能偷偷换模型或服务商。
- 第一版是 API 聊天 Bot，不具备执行命令、文件操作或浏览器控制能力。

### 会谈：独立的成员与消息空间

用户选择 Bot 创建会谈。支持一个或多个 Bot：一个成员可单独讨论，两个以上形成多方会谈。会谈成员数量不设固定上限，与官网分屏数量无关。

- 会谈有标题、成员、消息记录和最近活动时间；可重命名和删除。
- 同一个 Bot 可以加入多个会谈，各会谈历史独立，不互相泄漏。
- 创建后保存成员的名称、模型和角色快照。修改 Bot 模板只影响以后创建的会谈。
- 会谈空闲时可以增减成员或修改成员模型、角色；已发出的消息保留当时身份，新设置只作用于后续请求。
- 新加入的成员在首次被要求回答时可读取本会谈历史；加入时明确提示这一点。
- 删除 Bot 模板不删除历史会谈；历史成员仍使用自己的快照。没有成员时只能阅读历史，补充成员后才能发送。

## 4. 主界面

主入口为“内嵌官网 / Bot 会谈”。Bot 会谈替代原 API 模式，主区域展示会谈界面：

- 左侧：会谈列表、“新建会谈”和“管理 Bot”。
- 顶部：会谈标题、成员列表、会谈设置。
- 中间：按轮次组织的聊天记录，显示用户、Bot 名称、真实模型、生成状态和正文。
- 底部：输入框、明确的接收对象、发送按钮，以及“互评一轮”“生成总结”。

首次进入按“配置服务 → 创建 Bot → 创建会谈”的顺序引导。配置完成后可直接进入 Bot 创建，不让用户保存 Key 后找不到使用入口。

创建 Bot 需要名称和模型，角色说明可选。创建会谈只需选择成员，标题可默认使用首条问题的简短文本，用户可修改，不额外调用模型起名。

同一轮并行回复按发起时的成员顺序占位，分别流式更新，完成快慢不改变排列顺序。每条回复可复制、引用；失败消息可单独重试。

窄窗口下，会谈列表收进抽屉，成员和工具动作可以折叠，输入区保持可见。中文与英文完整支持。并排比较视图后置，第一版只做群聊主视图。

## 5. 会谈规则：共享历史，用户控制发言

第一版不设置隐藏的主持模型，也不让 Bot 自行无限互相叫醒。每次用户操作对应明确的目标和有限请求。

| 操作 | 接收者 | 行为与结束条件 |
|---|---|---|
| 普通发送 | 默认全体当前成员 | 每个成员并行回答一次，结束后等待用户 |
| 指定回应 | 输入区选择一个或多个成员，也支持从候选列表插入 @成员 | 仅选中成员各回答一次 |
| 引用回复 | 用户选中的接收者 | 携带引用内容及相关会谈历史，请指定成员回应 |
| 互评一轮 | 用户确认的成员，默认全体 | 阅读此前完整回复，各补充或审查一次，随后停止 |
| 生成总结 | 用户选择的一个成员 | 生成一条独立总结消息，随后停止 |

发送按钮明确显示“发送给全部 3 位成员”或“发送给方案顾问”等文案。收件人选择器是最终依据；@候选选择同步更新收件人，普通粘贴文本、代码块和 Bot 回复中的 @ 不自动触发调用。未识别的名字不静默扩大发送范围。

“互评一轮”不是强制反对：要求成员检查正确性、遗漏、依据与分歧，可以明确认同；不要为制造讨论而虚构异议。

至少有两位成员的完整回答后启用互评。存在失败成员时提示本轮缺席情况，用户可以重试，或明确选择基于已有回答继续。点击互评前展示参与者和本轮将产生的请求数量。

第一版同一会谈同一时间只有一轮运行。生成中允许编辑草稿、切换阅读其他会谈；本会谈的新发送、互评、总结和成员修改需等待或先停止当前轮。不排队自动补发。

## 6. 上下文：所有成员看到什么

群聊共享的是会谈记录，不代表一次生成中的模型能实时读到别人正在输出的文字。

1. 每轮开始时固定一份上下文，包含截止本轮开始前的历史和用户本次指令。
2. 同轮所有成员读取相同的历史范围，并分别附加自己的角色说明；不会读取本轮较快成员的答案，避免完成速度改变讨论条件。
3. 本轮结束后，完整回答进入历史。用户追问或发起互评时，成员才能看到这些新回答。
4. 其他 Bot 的回答以带身份的讨论材料提供，不能冒充当前 Bot 的亲身经历、用户命令或系统指令。
5. 用户引用的消息保留来源。互评、总结等操作在历史中保留可读记录；应用每次生成的任务模板不反复嵌套进正文。

默认只使用当前会谈历史，不自动引入其他会谈、Bot 私聊或长期记忆。用户当前明确要求优先于 Bot 的角色设定。

长会谈需要有限上下文：保留当前问题、显式引用及最近完整轮次；旧内容需要省略时，在发送前提示历史范围，并让模型知道存在省略。轮次尽量整体保留，避免只保留某一方观点。显式引用也放不下时，要求用户缩小范围，不静默截断。第一版不做隐藏的自动压缩总结。

## 7. 停止、失败与恢复

- 可以停止当前轮的全部生成，也可以停止某一位成员；不影响已完成回复。
- 已接收的部分正文保留并标记“已停止”“连接中断”等，默认不作为完整回答用于后续讨论或总结。
- 单个请求失败不会取消其他成员，也不会自动换模型或自动重试产生额外费用。
- 重试只重试选中成员，沿用原轮的问题、上下文和成员配置，保留原失败记录；成功后以后续上下文中的成功版本为准，不重复纳入失败片段。
- 后续轮已经开始后，不允许把迟来的重试结果补进旧轮；改为显式发起新的补充回答。
- 切换会谈或入口模式不会自动停止请求；列表显示仍在生成的会谈。关闭应用后未完成请求标记为中断，重启不自动续发。
- 删除正在运行的会谈前先确认并停止请求；删除后忽略晚到的数据，不能让已删除会谈重新出现。
- 停止本地请求不保证服务商不计费，不作“停止即免费”的承诺。

## 8. 总结与文档沉淀

用户选择总结者后，默认基于截至当前的完整会谈记录生成：原问题、共识、分歧、依据不足之处、待确认事项与下一步。总结保留为新消息，不覆盖原回答。

生成前展示使用的历史范围和缺席成员。若只能读取截短历史，应标记为“基于所选范围的总结”，不能声称覆盖完整会谈。

总结提供复制 Markdown 和保存 `.md`。第一版沿用已有记忆收件箱：用户将文档保存到自己授权的目录，再预览确认导入长期记忆。保存文件不等于导入记忆；会谈记录本身也不自动成为长期记忆。

直接从总结消息打开记忆导入表单可作为后续便捷功能，不另建记忆库，不省略用户确认。

## 9. 服务配置、本地记录与使用提示

### 9.1 第三方平台：一个 Key，多个模型

第一版继续使用一个 OpenAI-compatible 服务入口（兼容聊天 API 的服务地址）和一个 Key。入口可以是第三方模型聚合平台，也可以是提供兼容接口的模型厂商或自建服务；多 Bot 可选择该入口下有权调用的不同聊天模型。

“一个服务入口”限制的是同时配置的平台凭据数量，不是模型厂商数量。同一聚合平台下，不同厂商的模型可以分别成为会谈成员。第一版不新增同时管理多个平台、多个 Key 的能力。

典型流程：配置平台地址和 Key → 获取模型列表或填写模型 ID → 分别创建模型 A、B、C 对应的 Bot → 加入同一会谈 → 一次提问分别获得三方回答 → 指定互评或总结。三个 Bot 共用平台凭据，但每个 Bot 都发起独立请求，平台按实际请求和自身规则计费；一个 Key 不代表一次请求或只收取一份费用。

安装官方 CLI Agent 是另一种接入方式，需要处理本机安装、登录、权限和运行状态，后续单独评审。本方案第一版的 API Bot 无需安装官方 Agent；官方 Agent 与 API Bot 混合群聊也不属于本次已确认范围。

### 9.2 模型选择与兼容范围

模型列表保留当前发现能力，并允许手动填写服务商提供的模型 ID；不能因品牌筛选或推荐列表而让合法模型无法用于 Bot。手动模型的可用性由实际连接结果确定，不把它显示为已验证。

推荐模型仅帮助选择，不能充当模型白名单。不提供模型列表的兼容平台仍可通过手动模型 ID 配置；列表中出现某个模型也不代表当前 Key 已获调用权限。不支持聊天的模型不作为会谈成员；接口不兼容、模型无权限、余额不足或平台限流时，明确显示失败原因，不自动更换模型。第一版只承诺兼容聊天接口的接入范围，不承诺任意第三方平台及其全部专有功能。

### 9.3 凭据、记录与使用提示

服务地址变更时，明确提示会影响现有 Bot 的后续请求，不能把已保存的旧 Key 自动发给新地址。新地址的凭据须由用户明确配置，模型绑定重新检查，不能默默映射为另一个模型。

Bot、会谈和消息只在本机保存。首次使用说明“历史保存在本机；每次发送会把本次所需的会谈内容交给配置的模型服务”。不把本地保存描述成数据从不离开设备。

使用第三方聚合平台时，发送内容会交给该平台，并可能按其服务规则转交模型提供方处理。配置与发送界面应让用户能够确认当前平台和目标模型。

普通会谈历史与诊断日志分开：前者用于用户恢复讨论，可单独删除；后者不保存消息正文和 Key。删除会谈不删除已经单独保存的文件或确认导入的记忆，删除界面说明该范围。

继续使用系统安全存储保护 Key，界面不回显完整 Key。每轮显示目标数、状态和耗时；服务返回用量时可展示实际用量，不返回则显示“未提供”。本次不引入价格维护、自动预算系统或诊断正文采集。

现有 `api-conversation-governance-proposal.md` 仍是独立的待评审建议，不能把其中敏感信息扫描、预算和审计系统当作已经实现，或全部并入本次开发。

## 10. 从现有 API 模式过渡

- 保留已有服务地址、加密 Key 和模型配置。
- 首次进入新版时提供“用现有模型创建会谈”，按已配置格子顺序生成 Bot 草稿；同模型的多个格子明确显示重复模型，由用户决定是否保留。
- 用户确认后一次性创建会谈，记录完成状态，重复启动不重复生成。
- 当前 API 回答没有可靠的持久化历史，不伪造迁移记录、不承诺恢复过去的会谈。
- API 模式改用会谈列表、Bot 和群聊，不再使用格子激活开关、网页导航与拖动转发。官网布局、标签页和登录状态保持独立。

## 11. 第一版范围与后续方向

第一版包含：第三方兼容平台接入、一个 Key 调用多个不同模型、Bot 创建与管理、单成员或多成员会谈、单成员聊天、全体并行回答、指定成员、引用、互评一轮、多轮上下文、本地历史、停止与单成员重试、独立总结和 Markdown 保存。

后续单独评审：自主主持与多轮自动讨论、更多成员、并排对比、多服务商 Key、文件附件、联网搜索、CLI Agent、工具执行、Bot 私信、长期记忆自动召回、云同步、托管额度与付费。

上述范围是本方案确认的产品边界，不把 Termany 已有功能自动视为本项目必须照搬的需求。

## 12. 验收场景

1. 配好一个服务后创建三个不同模型 Bot，加入会谈；一次提问三个请求并发启动，分别流式显示。
2. 首轮较快回答不会进入较慢成员的同轮输入；排列稳定，不按完成速度跳动。
3. 用户追问时，各目标可看到此前的用户问题和完整成员回答，旧消息不被覆盖。
4. 指定一位成员时只产生一个请求；引用另一成员回答无需手动复制；正文中的普通 @ 不产生额外请求。
5. 互评一轮让指定成员各回应一次，全部完成后停止，不出现 Bot 自动连锁调用。
6. 同模型的两个不同角色 Bot 独立输出，不因模型名相同而混流；同一 Bot 的两个会谈不串历史。
7. 某位成员超时，其他成员继续；单独重试不重复用户消息或其他成员调用，部分回答不假装完整。
8. 停止、切换会谈、切换官网模式、删除会谈或重启后，晚到响应不覆盖其他会谈和轮次。
9. 总结包含原问题和讨论演变，明确分歧和缺席信息；保存后原回答仍存在，未确认不进入长期记忆。
10. 长上下文发生裁切时，用户与模型都知道范围；不静默遗漏显式引用或只保留一方观点。
11. 修改 Bot 模板或会谈成员不改写历史身份；更换服务地址不会向新地址泄露旧 Key。
12. 官网发送、读取、转发和现有记忆流程回归通过；窄窗口和中英文可用，Key 与消息正文不进入诊断日志。
13. 未安装任何官方 Agent 时，配置一个兼容聚合平台地址和 Key，即可让该平台下三个不同厂商的模型参与同一会谈；各请求使用对应模型 ID，共用该平台凭据，成员详情可确认平台与模型。
14. 不在推荐品牌列表中的聊天模型仍可创建 Bot；平台不提供模型列表时可手动填写模型 ID。无权限、余额不足或限流时只标记对应请求失败，不悄悄换模型或重复收费重试。

上述场景是验收要求。模块和界面已接入不代表验收通过；逐项现状见[实施状态](api-bot-group-conversation-implementation.md)。修复后应完成相关自动化验证、项目测试、生产构建及桌面端到端验收。
