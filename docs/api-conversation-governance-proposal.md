# MultiMind Flow API 对话治理方案

> 状态：设计建议  
> 日期：2026-07-25

## 1. 目标

API 对话模式会把用户输入直接发送给外部模型服务。项目需要在扩展更多服务商和
模型之前，建立轻量、可解释的治理边界：

- 发送前提示可能泄露的敏感信息。
- 展示可理解的用量和费用估算。
- 保留不包含对话正文的最小运行记录。
- 继续使用本地、安全的凭据存储。

治理能力服务于用户知情和控制，不代表产品已经获得任何行业合规认证。

## 2. 适用范围

第一版只覆盖 MultiMind Flow 主动发起的 API 请求，包括：

- 底部输入向多个 API 模型并发发送。
- API 模型之间的转发、审查和总结。
- 未来由任务编排器发起的 API 步骤。

嵌入式 AI 网站由网站自身发起网络请求，应用无法可靠观察其 token、费用或完整
数据流。因此界面必须区分“API 模式治理”和“网站服务自身的数据政策”，不能让
用户误以为同一套审计和预算能力覆盖嵌入网页。

## 3. 请求处理顺序

所有 API 请求统一经过以下顺序：

```text
构造请求
  -> 本地敏感信息检查
  -> 用户确认、遮盖或取消
  -> 预算预检
  -> 服务商调用
  -> 汇总用量、耗时和状态
  -> 写入最小审计事件
```

并发 fan-out 仍应并发执行。某个模型被敏感信息策略拦截、超预算或调用失败，
只能影响该目标，不能阻塞其它已经获准的目标。

## 4. 敏感信息检查

### 4.1 第一版检测范围

优先支持高确定性的本地规则：

- 常见 API Key、Access Token 和私钥片段。
- 中国大陆身份证号、手机号和银行卡号候选。
- 邮箱地址。
- 用户自定义的敏感词或固定标识符，作为后续能力。

检测应返回类型、位置和置信等级，不把检测到的原值写入日志。

### 4.2 用户操作

发送前提供三种明确选择：

- 继续发送原文。
- 使用预览后的遮盖文本发送。
- 取消本次请求。

默认不在后台静默改写用户文本。高风险凭据可以默认阻止并要求用户显式确认，
普通邮箱、手机号等默认警告即可。用户的单次选择不应自动变成永久全局许可。

### 4.3 遮盖语义

遮盖使用带类型的占位符，例如 `[EMAIL_1]`、`[PHONE_1]`。同一请求内相同原值
应映射到同一占位符，便于模型理解上下文；映射只存在于当前请求内，请求结束后
立即释放，不持久化原值。

## 5. 用量和预算

### 5.1 数据来源

优先采用服务商响应中的实际 token usage。服务商不返回 usage 时才使用本地估算，
并在界面明确标记“估算”。

价格表需要包含来源和更新时间。未知模型或价格过期时只展示 token，不伪造费用。

### 5.2 预算层级

第一版建议支持：

- 单次任务预计费用提醒。
- 本地月度软预算。
- 达到阈值时警告，超过预算时由用户决定是否继续。

预算默认是提醒和保护机制，不是财务账单。所有币种换算都必须显示采用的汇率或
直接保留服务商计价币种。

## 6. 最小审计事件

默认只记录诊断和用量元数据：

```typescript
interface ApiAuditEvent {
  id: string;
  taskRunId?: string;
  requestId: string;
  providerId: string;
  model: string;
  startedAt: number;
  completedAt?: number;
  status: "completed" | "failed" | "cancelled" | "blocked";
  elapsedMs?: number;
  inputTokens?: number;
  outputTokens?: number;
  estimatedCost?: number;
  costCurrency?: string;
  usageEstimated: boolean;
  piiFindingTypes: string[];
  errorCode?: string;
}
```

默认禁止写入：

- API Key 或认证头。
- 检测到的敏感原值。
- 完整 prompt 和完整模型回答。
- 请求/响应原始报文。

如果未来增加“保存对话用于诊断”，必须单独征得用户同意，提供保留期限和清除
入口，并与正常审计记录分开存储。

## 7. 凭据与本地数据

- API Key 继续使用 Electron `safeStorage`，不降级为明文配置文件。
- 渲染进程不应获得可直接读取的明文 Key。
- 日志、异常消息和导出的诊断信息必须先清除认证信息。
- 审计记录和预算统计默认只保存在本地。
- 清除 API 配置时，应允许用户同时清除相关用量和审计元数据。

## 8. 架构边界

建议使用小型 TypeScript 服务，而不是引入完整的外部 Agent/RAG SDK：

```text
apiConversationService
  -> apiRequestGuard
  -> apiBudgetService
  -> provider adapter
  -> apiAuditStore
```

服务商差异由 provider adapter 处理；敏感信息、预算和审计规则保持服务商无关。
第一版继续以 OpenAI-compatible 接口为主，只有在真实需求验证后才扩展多套凭据、
路由、失败回退和上下文迁移。

不要为了预留扩展而引入 Python 常驻服务、大型统一 SDK、远程向量数据库或几十种
未使用的服务商适配器。它们会增加 Windows 打包、更新、子进程清理和故障诊断成本。

## 9. 建议实施顺序

### 阶段 A：审计底座

- 统一请求 ID 和任务关联。
- 记录状态、耗时和实际/估算 token。
- 验证日志中不存在凭据和对话正文。

### 阶段 B：敏感信息预检

- 本地高确定性规则。
- 高亮预览、遮盖、继续和取消。
- 多模型 fan-out 中按目标记录 blocked/cancelled 状态。

### 阶段 C：预算提示

- 模型价格元数据和更新时间。
- 单次任务预估与实际用量。
- 本地月度软预算。

### 阶段 D：多服务商能力

仅在用户确实需要多个服务商时再增加统一 provider 接口、按模型选择凭据和明确的
失败回退策略。自动路由不得在未提示用户的情况下把内容改发到另一个服务商。

## 10. 验收边界

- 凭据类敏感信息能在网络请求前被拦截。
- 用户能看到即将发送的原文或遮盖后文本。
- 取消或阻止某个目标不会拖住其它并发目标。
- 实际 usage 优先于估算，未知价格不展示虚假金额。
- 默认审计数据不含 API Key、敏感原值、prompt 和回答正文。
- 用户可以查看并清除本地审计和预算数据。
- UI 明确区分 API 模式治理与嵌入式网站的数据处理边界。

## 11. 暂不实施

- 宣称满足 GDPR、HIPAA、SOC 2 等认证。
- 自动上传审计日志。
- 默认保存完整 API 对话用于分析。
- 无用户确认的跨服务商自动路由。
- 将整套第三方 Agent、RAG 或合规 SDK 嵌入桌面应用。
