# 应用内更新方案（待执行）

状态：方案评审稿。除独立完成的“启动时自动检查新版本”勾选项外，本文的新下载、覆盖安装和恢复流程尚未实现。当前实现说明见 [应用更新](app-updates.md)。

## 目标与范围

用户在应用中完成“检查新版本 → 查看更新内容 → 下载 → 重启并覆盖安装 → 回到原有工作区”。正式更新仍托管在 GitHub Releases，不要求用户跳转网页寻找安装包。

首期支持当前发布的平台：macOS Universal 与 Windows x64。不增加强制更新、后台自动下载安装或降级入口，不更换现有桌面技术栈。

不依赖 Apple Developer ID 证书实现自定义 macOS 替换流程，但需要我们自己的更新包签名密钥来验证来源。两者用途不同：更新包验签保护下载和安装内容，不能代替 macOS 的应用身份认证和公证，也不能保证系统不会要求用户确认打开。

## 用户流程

1. 设置中显示当前版本、检查结果和“检查更新”按钮。
2. “启动时自动检查新版本”为勾选框，默认关闭，立即保存到本机。未勾选时，启动不发起更新检查；手动检查始终可用。关闭不会取消用户已主动开始的下载。
3. 发现新版后显示版本号、更新说明、下载大小和“下载更新”。自动检查只显示不打断操作的提示，不自动下载，也不弹出强制安装窗口。
4. 下载中显示进度、已下载大小，并提供“取消下载”。网络失败保留旧版正常运行，允许重试。
5. 下载并校验成功后显示“重启并安装”和“稍后”。用户关闭设置或退出应用都不擅自安装；再次启动后重新验证已下载文件，再恢复待安装提示。
6. 用户点击安装时，检查所有会谈生成、互评、总结、文档任务和终端任务。仍有任务时提示先完成或停止，不自动中断。无法可靠判断的活跃终端需要用户明确处理。
7. 保存设置、未发送草稿、当前会谈及数据库写入，进入安装状态并停止接受新任务。若保存失败，则留在当前版本。
8. 安装后重新打开应用，恢复工作区，并显示“已更新到 x.x.x”。失败时说明“旧版本仍可使用”或提供明确的恢复步骤。

界面不向用户展示校验和、证书路径、安装脚本等实现信息。需要授权时说明实际操作，例如“需要允许替换应用”。

## 状态与失败提示

| 状态 | 用户能做什么 | 失败处理 |
| --- | --- | --- |
| 未检查／已是最新 | 检查更新、调整自动检查开关 | 不影响聊天 |
| 检查中 | 等待结果 | 超时后可重试，不能误报“已是最新” |
| 有新版本 | 查看说明、下载 | 不自动打开网页 |
| 下载中 | 查看进度、取消 | 可重试，旧版不受影响 |
| 校验中 | 等待 | 校验失败删除不可信缓存，禁止安装 |
| 待安装 | 重启并安装、稍后 | 已下载文件丢失则重新下载 |
| 正在安装 | 等待 | 安装器记录结果，按平台恢复 |
| 已更新／已恢复 | 继续使用 | 保留可读的失败原因与重试入口 |

首期采用完整包下载；取消或中断后重新下载，不承诺断点续传。只有校验完成的缓存可复用。

## 更新源与发布文件

更新仓库继续从现有发布配置读取，使用 `pairusuo/multimind-flow`，不在多个文件重复硬编码。

每个正式 Release 除现有安装包外，增加一个签名更新清单及对应签名文件。清单包含：格式版本、应用身份、版本号、发布说明、最低系统要求、每个平台/架构的文件名、大小与 SHA-256。应用内置更新公钥，私钥仅保存在发布环境，不进入仓库或安装包。

- macOS：增加专门用于更新的 ZIP，包含完整 Universal `.app`；DMG 继续供首次安装和人工恢复使用。
- Windows：保留 NSIS `.exe`、`.blockmap`、`latest.yml`，以同一构建产物生成签名清单。
- 应用只接受正确应用身份、支持平台和架构、比当前版本更新的正式发布。草稿、预发布、缺少更新清单或缺少匹配产物不能显示为可安装更新。
- 下载地址必须绑定对应 GitHub Release 资产，使用 HTTPS，并限制重定向目标；不接受清单中的任意执行命令、本机路径或脚本。
- 发布流程先上传全部产物和清单，再公开 Release，避免用户看到文件未齐的新版。
- 私钥丢失时不能继续使用原密钥发布；密钥轮换要提前通过旧密钥签名的版本引入新公钥。首期先固定一个公钥并备份私钥，不设计远程关闭验签的开关。

## macOS 覆盖安装

采用独立的本地更新助手，不调用要求应用签名的 Squirrel.Mac 自动安装路径。

1. 应用主进程下载并验证签名清单及 ZIP 的大小、哈希。解压到独立暂存目录，限制文件数量和总大小，拒绝目录穿越及越界符号链接。
2. 校验 `.app` 的应用标识、版本、主程序和架构；确认是完整应用包，不接受只替换 `app.asar` 的做法。
3. 检查真实安装路径、可写权限及可用空间。对从 DMG、临时目录或 App Translocation 运行的实例，提示先安装到“应用程序”，不尝试覆盖临时副本。保留用户自行选择的正常安装路径，不默认安装到另一个目录。
4. 用户点击“重启并安装”后先保存数据。更新助手在应用退出后再次校验暂存包，然后开始替换。
5. 在目标应用同一文件系统暂存新版，将旧应用重命名为备份，再将完整新版移到原路径。任何一步失败恢复旧路径；保留安装日志和事务标记，以应对断电、崩溃和重复启动。
6. 重启成功后，新版在初始化完成且数据可读取后向助手确认。未经确认不删除旧版备份。
7. 如果新版无法启动，恢复旧应用并显示恢复结果。若数据库已经执行不向后兼容的迁移，不直接让旧版打开新数据库：升级前需一致性备份，并禁止确认成功前产生新的用户写入；恢复时连同升级前的数据状态一起恢复。
8. 清理过期安装缓存和已确认不再需要的旧包。

首期不自动提权，不删除 quarantine 属性，不关闭 Gatekeeper。目标目录不可写时保留已下载安装包并提示用户打开安装包完成替换。系统授权或安全确认由用户完成，不能宣称所有设备都能静默覆盖。

关键待验证点：未签名/临时签名的更新助手在目标 macOS 环境下能否稳定运行；新包的 quarantine 行为；应用替换后的钥匙串访问；Intel 与 Apple Silicon 的原生依赖是否能正常加载。这些必须用实际打包产物验证，不能仅凭开发环境测试宣布支持。

## Windows 覆盖安装

继续使用 NSIS 安装器覆盖安装，不自行复制正在使用的 EXE。

- 保持现有应用标识、安装位置和当前用户／所有用户安装范围，不新建第二份应用。
- 下载产物必须先通过签名清单和哈希验证，再交给既有更新安装链路执行；版本描述文件与验签产物不一致时拒绝安装。
- 安装前保存数据并关闭应用。需要管理员权限时由系统显示 UAC；用户取消则保留旧版和待安装状态。
- 保留配置、Bot、会谈、记忆库与凭据，不执行卸载清理。
- 安装器失败或断电后验证实际安装状态。首期不承诺 NSIS 在任意故障下都能事务回滚；保留数据备份、安装日志和原安装包恢复入口。恢复失败不能显示“已更新”。

## 实现边界与顺序

1. 固定状态、IPC 类型、持久化设置和缓存结构；更新服务在应用生命周期内只初始化一次，避免重新打开窗口产生重复检查和监听。
2. 增加发布清单生成、签名和验签工具；提供不含真实私钥的发布配置示例。
3. 实现平台产物选择、可取消下载、校验、待安装状态持久化和界面提示。
4. 实现 macOS 更新助手、替换事务、健康确认和回滚；接入 Windows 既有安装器。
5. 完成下列验收后才打包发布。初次引入自定义更新能力的版本需要用户手动安装一次，已有旧版不会凭空获得新更新流程。

所有下载、验签和安装在主进程或受控助手中完成。渲染进程只提交固定动作、显示状态，不能提供安装命令或任意写入路径。

## 验收条件

- 自动检查关闭时，重启不请求更新服务；开启后下次启动检查，设置跨重启保存；手动检查不受开关影响。
- 检查失败、GitHub 限流、网络离线分别正确提示；多次点击不产生重复下载或安装。
- 错误签名、错误应用身份、错误架构、损坏文件、清单和安装包版本不一致一律拒绝安装。
- 下载取消、应用退出、重启、缓存损坏均能恢复到可操作状态。
- 生成、互评、总结、终端工作时不误退出；安装期间阻止新任务和第二个安装实例。
- macOS 用两个真实版本在 Apple Silicon 与 Intel 上验证覆盖、重启、目录权限不足、DMG 运行、替换失败、断电事务恢复、新版启动失败及回滚。
- Windows 验证当前用户／所有用户安装、自定义安装路径、UAC 取消、文件占用、安装失败和重启。
- 升级后 Bot、会谈历史、头像、设置、登录复用及记忆库保持可用；数据迁移和回滚不能丢失已确认保存的数据。
- 无签名版本的系统安全确认行为如实记录；不能以关闭系统保护作为测试通过条件。

## 依据

- [Electron 自动更新](https://www.electron.build/docs/features/auto-update/)：macOS 标准自动更新要求代码签名。
- [Tauri 更新验签](https://v2.tauri.app/plugin/updater/)：更新公钥／私钥与更新产物验证机制，用于区分更新包签名和 Apple 签名；本方案不迁移到 Tauri。
